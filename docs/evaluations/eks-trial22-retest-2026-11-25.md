# EKS Readiness 오류의 복구 판단 개선과 대안 비교

2026년 11월 25일, 기존 100회 평가 중 22회차만 같은 조건으로 다시 실측했다. 이어 같은 실측 자료로 모델 입력 세 가지를 비교하고, 별도 임시 Deployment에서 Kubernetes 대응 방법을 직접 비교했다. 기존 100회 원본은 변경하지 않았다.

## 1. 문제 정의 — 원인은 찾았지만 복원할 버전을 확신하지 못했다

기존 22회차는 Readiness 검사 경로를 `/readyz`에서 `/ready`로 바꾸는 실험이었다. Pod는 실행 중이지만 검사 요청이 404를 반환해 Ready 엔드포인트가 0개가 됐고, 서비스 요청 72건이 모두 실패했다. 모델은 원인을 찾았지만 정상 복원 버전의 근거가 부족하다며 사람 인계를 선택했다. 채점 기준은 중대 장애·운영자 승인 후 실행·롤백이었다.

Recreate는 이전 Pod를 먼저 종료한다. 따라서 현재 이전 Pod가 0개라는 사실과 과거 그 버전이 정상 응답했다는 사실은 구분해야 한다. 기존 입력의 정상 HTTP 관측에는 정확한 리비전과 템플릿 연결이 빠져 있었다.

## 2. 대안 도출 — Kubernetes의 상태와 변경 이력을 순서대로 확인했다

| 점검 항목 | 확인하려는 것 |
|---|---|
| Pod Running, Ready, 재시작 횟수 | 프로세스 실행과 트래픽 수신 준비를 구분 |
| Service의 Ready 엔드포인트 | Service가 요청을 전달할 대상이 있는지 확인 |
| Readiness 이벤트와 실제 HTTP 경로 | 앱 전체가 멈춘 것인지, 검사 경로 설정이 잘못됐는지 확인 |
| 배포 전후 변경과 리비전 | 어느 변경 뒤 문제가 생겼고 어떤 버전을 복원할지 확인 |
| 정상 응답 시각·Deployment UID·템플릿 | 과거 정상 상태와 복원 후보가 같은 배포인지 확인 |

재시작, 기본 롤백, 확인된 정상 버전 지정 복원을 비교 대상으로 정했다. 모델에는 기존 자료, 런북 설명만 보강한 자료, 정상 리비전 이력까지 추가한 자료를 각각 제공했다.

## 3. 비교 검증 — 동일 오류에서 대응 방법별 결과 확인

기존 EKS 워커에 임시 Deployment와 Service를 만들어 기존 `demo/api`와 분리했다. Pod 한 개, Recreate 전략, 같은 앱 템플릿을 사용했다. 각 단계에서 동일 Service에 HTTP 요청을 4번 보냈다. 이 테스트의 요청은 임시 대상의 기능 확인용이며 100회 평가 표본에 합산하지 않았다.

| 단계 | 리비전 | Readiness 경로 | Ready / 엔드포인트 | Service HTTP |
|---|---:|---|---|---|
| 정상 기준 | 1 | `/readyz` | 1 / 1 | 4/4 성공 |
| 오류 재현 | 2 | `/ready` | 0 / 0 | 4/4 연결 실패 |
| Deployment 재시작 | 3 | `/ready` | 0 / 0 | 4/4 연결 실패 |
| 기본 롤백 | 4 | `/ready` | 0 / 0 | 4/4 연결 실패 |
| 확인된 정상 리비전 1로 복원 | 5 | `/readyz` | 1 / 1 | 4/4 성공 |

실패 단계에도 Pod는 Running이었고, Pod IP의 실제 `/readyz` 경로는 각각 4/4 성공했다. 재시작은 검사 경로를 고치지 못했다. 재시작도 새 배포 리비전을 만들기 때문에 기본 롤백은 잘못된 경로가 있던 리비전 2의 템플릿으로 돌아갔다. 정상 응답을 확인한 리비전 1을 지정했을 때 서비스가 회복됐다. 이는 운영에서 무조건 재시작이나 롤백을 시도하라는 권고가 아니라, 격리된 실습에서 각 방법의 적용 한계를 확인한 비교다.

모델 비교에는 22회차 재검증의 동일 HTTP 76건과 운영 근거를 고정했다. 모델은 `gpt-5.6-terra`, 프롬프트는 `rag-decision-v3.0`이며 각 조건을 한 번씩 실행했다. 검색 문서 목록과 나머지 입력을 고정하고 리비전 복구 런북의 설명 및 정상 이력 근거만 바꿨다.

| 모델 입력 | 등급 | 처리 방식 | 선택한 조치 |
|---|---|---|---|
| A. 기존 근거·기존 런북 | 중대 장애 | 사람 인계 | 수동 확인 |
| B. 기존 근거·보강한 런북 | 중대 장애 | 사람 인계 | 수동 확인 |
| C. 정상 리비전 이력·보강한 런북 | 중대 장애 | 운영자 승인 후 실행 | 롤백 |

설명만 보강한 B에서는 정상 복원 버전의 식별 정보가 부족하다는 판단이 유지됐다. C에서는 과거 정상 HTTP, 동일 Deployment 소유자와 일치하는 직전 템플릿을 근거로 승인 롤백을 선택했다. 결과를 정답에 맞게 바꾸거나 기대 등급·처리 방식·시드를 모델에 제공하지 않았다.

## 4. 점진 적용 — 22회차만 별도로 재검증

`baseline-revision-v1`은 정상 HTTP 수집 전후 Deployment의 UID·세대·리비전이 같은지 확인하고, 당시 가용 ReplicaSet의 템플릿 해시를 저장한다. 장애 후 같은 소유자의 직전 템플릿과 대조한 결과를 모델에 제공한다. 런북 3.0에는 Recreate의 현재 이전 Pod 수와 과거 정상 이력을 구분하는 설명을 추가했다.

원본 22회차의 시드 `637468554`, 복제본 1개, 초당 배경 요청 20건, 장애 관측 180초 등 저장된 조건을 유지했다. 새 실측에서 76/76건 실패를 확인했고, 모델은 중대 장애·승인·롤백을 선택해 세 기준에 일치했다. 정상으로 확인된 리비전은 154, 실패한 새 리비전은 155였으며, 모델은 이력 대조 근거를 직접 인용했다.

에이전트 평가는 판정까지만 수행했다. 실제 복원 동작 비교는 위의 격리된 임시 Deployment에서 운영자 실험 코드로 수행했다. 에이전트가 자동으로 복구했다고 집계하지 않는다.

## 5. 추가 개선 — 근거가 부족할 때는 복원을 확정하지 않는다

정상 HTTP가 확인 구간 밖에 있거나, Deployment 소유자·템플릿이 다르거나, 사이에 다른 리비전이 추가된 경우에는 정상 복원 후보로 확정하지 않는 테스트를 추가했다. 정답 정보가 모델 입력에 섞이지 않는 것과 원본을 보존한 단일 회차 재검증도 확인했다. 전체 단위 테스트 97개가 통과했다.

이번 실측은 한 회차, 모델 비교는 조건별 한 번이다. 다른 99회차나 전체 탐지 성능이 개선됐다는 결론으로 확대하지 않는다. 향후 다른 배포 장애에도 적용하려면 해당 조건을 별도로 검증해야 한다.

## 검증 자료와 재실행

- 원본: `eval/results/detection-20261124-155040-573677.json` — 100회 기록 유지
- 22회차 신규 실측: `eval/results/detection-20261125-163649-711175.json`
- 모델 세 조건 비교: `eval/comparisons/revision-trial22-20261125-164522.json`
- 격리 Kubernetes 비교: `eval/comparisons/trial22-check-df6702f1.json`
- 관련 코드: [리비전 근거](../../eval/revision_evidence.py), [단일 평가기](../../eval/single_detection.py), [모델 비교](../../eval/compare_revision_evidence.py), [격리 복구 비교](../../eval/readiness_recovery_lab.py)

원시 자료에는 실습 환경 식별자가 포함될 수 있어 Git에서 제외한다. 원본 평가 파일 10개의 SHA-256 불변을 확인했다. 신규 실측 종료 후 API·웹은 2/2 Ready, API 경로는 `/readyz`, 전략은 RollingUpdate로 원복됐다. 격리 실험은 원본 API의 spec·UID를 변경하지 않았고 임시 Service·Deployment를 삭제했다.

기존 AWS 세션과 EKS가 준비된 환경에서 다음 명령으로 한 회차를 다시 평가할 수 있다. 실제 장애 재현과 모델 호출이 발생하며 기존 유료 자원과 모델 사용량이 소모된다.

```bash
bash scripts/eks-lab.sh retest eval/results/detection-20261124-155040-573677.json 22
```

AWS_PROFILE과 KUBEOPS_AWS_ACCOUNT는 사용 중인 실습 계정에 맞춰 지정한다. 모델 비교는 `eval/compare_revision_evidence.py --report <단일 재검증 파일> --old-commit <보강 전 커밋>`으로 별도 실행한다. 격리 조치 비교는 `eval/readiness_recovery_lab.py`이며 임시 리소스를 생성하고 정리한다.
