# 18종 시나리오의 위험 등급과 복구 담당

## 표를 읽는 기준

위험 등급은 관측한 서비스 영향이고, 처리 방식은 마지막에 누가 무엇을 할지에 대한 판단이다. 기존 Pod가 요청을 처리하는 동안 새 배포만 막히면 **주의 + 사람이 직접 처리**가 가능하다. 재생 중 문제가 회복되면 같은 사건이 **주의 + 자동 관찰**이 될 수 있다.

- **정상**은 대표 앱 요청이 기준 이내이고 운영 이상도 없는 경우다. **주의**는 앱 요청이 기준 이내여도 배포·조회·쓰기 경고나 요청 지표 공백이 확인된 경우다.
- **장애**는 대표 HTTP 측정 묶음의 실패율이 5%를 초과하거나 p95 지연이 300ms를 초과한 경우, 또는 연결 가능한 엔드포인트가 사라진 경우다. **중대 장애**는 연결 대상이 사라지고 연속 두 유효 묶음의 요청이 모두 실패한 경우다. 재생 4종은 실측 Ready 엔드포인트 0개를 확인한 시각 직전 20초 안의 두 묶음을 사용한다. 충분한 근거를 확보하지 못하면 **판단 보류**로 남긴다.
- **자동 관찰**은 재측정·회복 확인이다. **제한 자동 조치**는 전용 로컬 kind의 demo/api에 대해 런북 조건을 충족한 직전 버전 롤백 또는 복제본 1개 추가다. **운영자 승인 후 에이전트 실행**은 대상과 정상 리비전 등 근거를 확인하고 사람이 승인한 뒤 에이전트가 변경하는 경로다. **사람이 직접 처리**는 운영자가 원인과 변경 범위를 확인해 직접 복원하는 경로다.
- 기존 14종에서는 독립 채점기가 정한 권장 경로, 모델 제안, 실제 실행 정책을 따로 기록한다. 워크로드 채점기 `workload-v3.0`은 같은 지속 포화에 대해 전용 kind의 제한 조건을 충족하면 자동 증설, EKS에서는 비용·용량 검토 인계를 기대한다. 복원 근거가 확인된 격리 배포 실패는 kind의 제한 조건을 충족하면 자동 롤백, EKS에서는 승인 롤백을 기대한다. EKS에 자동 변경을 제안했다가 실행 정책이 인계해도 모델 제안은 오답으로 집계한다. 승인 롤백은 모델이 승인 경로를 제안하고 모든 조건을 충족할 때 가능하다. EKS 증설은 비용·용량 검토 대상으로 인계한다. 참조 근거가 부족한 사례는 권장 경로 채점이 미확정일 수 있다.
- 1~14번에서 로컬은 Mac의 전용 kind 클러스터, AWS는 EKS와 EC2 워커다. 두 환경 모두 시드로 배경 요청량(15·20·25 req/s), 관측 시간, 시작 복제본, 증거 공개 범위 등이 바뀐다. 표에서 **새 버전/전체**는 순차 배포로 기존 Pod를 유지할지, 재생성 배포로 전체가 영향을 받을지를 뜻한다.
- 15~18번은 EKS 관측 Pod의 HTTP와 EndpointSlice를 읽고 같은 시간대의 Kubernetes 기록을 시드로 합성한다. 발생 시점 5·10초, 지속 시간 15·45·90초, 회복·지속이 바뀐다. 재생 평가는 실제 클러스터를 변경하지 않는다. 사람이 처리한다는 결과는 같은 증상이 실제 운영에서도 확인됐을 때의 담당을 뜻한다.

| 7 Readiness 실패 | 준비 검사 경로를 /readyz에서 /ready로 변경해 404 유발 | EKS에서 새 버전/전체. 실패한 Pod가 트래픽 대상에서 빠지는지 확인 | 기존 Ready Pod가 서비스하면 주의. 엔드포인트 소실 시 장애~중대 장애 | 검사 설정만 바뀐 경우 kind 제한 자동 롤백 후보. EKS는 승인 롤백 또는 인계. |

| 10 이미지 다운로드 실패 | 존재하지 않는 이미지 태그를 배포 | EKS에서 실행별 잘못된 태그로 새 버전/전체 배포 | 새 버전만 이미지 가져오기 실패 → 주의. 가용 복제본 소실 → 장애~중대 장애 | 직전 정상 이미지가 확인되면 승인 롤백. 이미지 변경은 인자·준비 검사 전용 자동 롤백 범위를 벗어난다. |

| 13 요청 지표 누락 | API Pod의 Prometheus 수집 annotation 비활성화 | EKS에서 해당 대상 수집을 끄고 워커 HTTP와 비교 | HTTP 정상이고 요청 지표가 비면 주의. 앱 영향 근거도 없으면 판단 보류 가능 | 첫 공백은 재측정. 연속 공백 확인 시 모니터링 담당자에게 인계. |

## 사람이 조치하는 경우

아래는 **실제 운영 증상이 확인됐을 때의 대응**이다. 등급은 대표적인 관측 조건이며 재생 4종의 합성 이벤트 자체는 운영 변경의 근거가 될 수 없다.

| 대상·사람이 맡는 조건 | 위험 등급 | 사람이 수행할 조치 | 복구 완료를 확인하는 근거 |
|---|---|---|---|
| 1·2 정상 대조가 깨지거나 재시도 후에도 실패 | 경고만 있으면 주의, 대표 요청 기준 초과 시 장애 | 워커의 정상 Service 요청과 실패한 echo의 시각·경로를 대조한다. 터널·프록시·클라이언트와 앱 중 실제로 실패한 경로의 담당자가 수정한다. | 원래 실패한 요청과 독립 워커 HTTP가 모두 정상 |
| 3 배포 후 지연 | 보통 장애 | 운영자가 배포 전후 지연과 직전 정상 리비전을 확인해 롤백을 승인한다. 승인이 차단되면 배포 담당자가 변경 충돌을 확인한 뒤 검증된 리비전으로 복원한다. | 롤아웃 완료, 같은 부하에서 p95 300ms 이하·실패율 5% 이하 |
| 4 Service selector 불일치 | 장애~중대 장애 | Service 담당자가 올바른 배포의 Pod 레이블과 원래 selector를 대조해 복원한다. 함께 바뀐 포트도 확인한다. | EndpointSlice에 Ready 주소가 생기고 Service DNS로 HTTP 성공 |
| 5·6·7·10 실패한 새 배포 | 주의~중대 장애 | 정상 리비전이 확인되면 승인 롤백. 수동 수정 시 5는 잘못된 인자, 6은 OOM 발생 직전 메모리 사용·제한, 7은 실제 준비 경로·포트, 10은 이미지 태그·digest·접근 권한을 확인한다. 검증된 매니페스트로 재배포한다. | 새 버전 Ready, 원래의 종료·검사·이미지 이벤트가 멎고 워커 HTTP 정상 |
| 8 EKS 지속 과부하 | 보통 장애 | 앱 담당자가 원래 부하와 지연·CPU 포화를 확인한다. 여유 EC2 용량을 먼저 확인하고, 병목에 맞춰 부하 제한 또는 Pod 증설을 결정한다. 워커 증설이 필요하면 비용·용량을 검토한다. | 같은 부하에서 요청 기준 충족, 새 Pending Pod 없음 |
| 9 CPU 부족 | 주의~중대 장애 | Pod 요청량과 노드에 남은 예약 가능 CPU를 비교한다. 실습처럼 비정상적으로 큰 요청은 적정값으로 복원하고, 실제 용량 부족이면 워커 사양·수량을 검토한다. | 새 Pod에 노드 할당·Ready, 새 FailedScheduling 경고 중단 |
| 11 DNS 오류 | 보통 주의, 대표 요청도 실패하면 장애 | 클라이언트의 서비스 이름·네임스페이스를 수정한다. 정상 이름도 여러 지점에서 실패한다면 DNS 설정·CoreDNS 상태와 네트워크 경로를 확인한다. | 원래 실패한 클라이언트에서 올바른 이름 해석과 HTTP 모두 성공 |
| 12 워커 점검 후 대체 Pod 미복구 | 주의~중대 장애 | 노드 담당자가 다른 워커의 Ready·예약 용량·배치 제약과 퇴거를 막는 PodDisruptionBudget을 확인한다. 점검이 끝나고 원래 노드가 정상일 때 신규 배치를 다시 허용한다. | 의도한 노드에 대체 Pod Ready, 서비스 요청 정상, 노드 스케줄 가능 상태가 계획과 일치 |
| 13 지표 공백 지속 | 보통 주의, 앱 영향 증거까지 부족하면 판단 보류 | 모니터링 담당자가 API Pod 수집 annotation·레이블과 Prometheus 대상 상태를 확인해 원래 수집 설정을 복원한다. | 새 요청을 보내는 동안 요청량·오류율·지연에 최신 표본이 다시 생성 |
| 14 PVC 대기 | 주의~중대 장애 | 스토리지 담당자가 요청한 StorageClass, PVC 이벤트, provisioner, 노드 가용 영역을 대조한다. 실습은 잘못된 클래스 참조를 바로잡는다. 기존 데이터가 있는 claim은 보존·이관 계획을 확인한다. | PVC Bound, Pod 마운트·Ready, 서비스 HTTP 성공 |
| 15 API 조회 시간 초과 지속 | 기본 주의, 앱 영향 시 장애~중대 장애 | 한 지점만 실패하면 해당 PC/VPC의 DNS·라우팅·엔드포인트 접근 설정을 확인한다. 양쪽이면 EKS 상태와 공통 경로를 점검하고, 지속 시 클러스터 식별자·시간대·양쪽 결과를 AWS 지원에 전달한다. | 양쪽에서 조회 성공. 쓰기 복구를 보고하려면 승인된 시험 변경과 저장값 재조회까지 확인 |
| 16 Pod 미배치 지속 | 기본 주의, 앱 영향 시 장애~중대 장애 | 노드 자원·taint·affinity·PVC와 배치 이벤트를 확인한다. 적합한 노드가 있고 배치 판단 자체가 계속 멈췄다면 시간순 Pod·리더 증거를 EKS 운영자와 AWS 지원에 전달한다. | 대상 Pod에 nodeName이 채워지고 Ready, 후속 앱 HTTP 정상 |
| 17 저장된 목표가 Pod로 반영되지 않음 | 기본 주의, 앱 영향 시 장애~중대 장애 | 배포 담당자가 Deployment의 목표·세대, ReplicaSet의 목표와 이벤트를 시간순으로 확인한다. 생성 거부·쿼터 등 확인된 원인을 수정하고, 관리형 컨트롤러 이상이 지속되면 AWS 지원에 인계한다. | 목표 수만큼 새 Pod가 실제로 생성·배치돼 Ready, 후속 HTTP 정상 |
| 18 API 쓰기 실패 지속 | 기본 주의, 앱 영향 시 장애~중대 장애 | 플랫폼 담당자가 정확한 쓰기 오류·조회 결과·시각을 보존한다. NOSPACE 근거가 있으면 EKS 관리형 저장소 문제로 AWS 지원에 인계한다. 일반 오류만 있으면 권한·쿼터·승인 정책 등 다른 실패 원인을 확인한다. | 승인된 작은 변경의 성공 응답과 변경값 재조회, 기존 앱 HTTP 정상 |
