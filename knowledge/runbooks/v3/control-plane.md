# EKS API 조회·쓰기와 Pod 생성·배치의 진행 판정
버전 3.0 · API timeout / scheduler / controller / etcd NOSPACE

## 관측 출처
재생에서는 EC2 워커의 앱 HTTP와 사용 가능한 EndpointSlice 관측이 실측이고 Kubernetes 운영 기록은 합성이다. 같은 클러스터·대상·시간대의 증거를 비교한다. 서비스 영향은 실제 HTTP로 판단하고, 운영 작업은 마지막으로 확인된 단계까지만 보고한다. 실제 EKS에서 동일 증상이 확인되면 팀 소유의 접속·워크로드 설정을 먼저 점검하고, 관리형 구성요소의 지속 장애는 시간순 증거와 함께 플랫폼 담당자에게 인계한다.

## API 조회 시간 초과
운영자 PC와 VPC 내부의 조회 결과를 따로 적는다. 한쪽만 반복 실패하고 다른 쪽이 성공하면 해당 지점의 DNS·라우팅·API 엔드포인트 접근 경로를 점검한다. 양쪽 모두 시간 초과이고 앱은 200이면 서비스 응답과 관리 API 조회 실패를 함께 보고한다. 시도하지 않은 쓰기의 성공·실패는 미확인이다. 양쪽 조회와 후속 앱 HTTP가 회복되면 관찰하고, 지속되면 담당자에게 인계한다.

## 새 Pod의 생성과 노드 할당
목표 복제본 변경이 저장됐는지 확인하고 여러 시점의 Pod UID와 nodeName을 비교한다. 새 Pod 오브젝트가 있으나 노드가 비어 있으면 배치 지연이다. 적합한 워커가 있는지, CPU 부족·배치 제약·PVC 이벤트가 있는지 확인한다. Insufficient cpu는 스케줄러가 내린 배치 거부 판단이다. 적합한 워커가 있는데 리더 갱신도 정체되면 스케줄러 이상을 의심한다. Pending만으로 원인을 확정할 수 없다.
목표가 저장된 뒤에도 새 Pod가 생기지 않으면 Deployment 세대와 ReplicaSet 이벤트를 대조하고 생성 지연으로 인계한다. 두 경우 모두 목표 수만큼 생성·할당·Ready가 되고 이후 앱 HTTP도 정상일 때 관찰로 종료한다.

## 읽기 성공과 쓰기 실패
조회 성공, ConfigMap 생성 또는 Deployment 변경의 실패 응답을 구분한다. 시간 초과된 변경의 저장 여부는 후속 조회가 있어야 확인된다. NOSPACE 근거가 있으면 etcd 공간 한도를 의심하고, 일반 쓰기 오류만 있으면 원인은 미확정이다. 쓰기 성공 응답, 변경값 재조회와 후속 앱 HTTP를 확인하면 관찰한다. 실패가 지속되면 원본 오류와 대상·시각을 플랫폼 담당자에게 전달한다.

## 재생에서의 처리
운영 문제가 지속되거나 마지막 회복을 입증할 자료가 부족하면 사람에게 인계한다. 관련 작업과 후속 앱 HTTP가 모두 회복되면 자동 관찰한다. 재생 판단은 권장 경로를 평가하는 데 사용하며 실제 EKS 변경이나 관리형 구성요소 재시작을 수행하지 않는다.
