# EKS에서 서비스 영향과 처리 담당 판단
버전 3.0 · EKS 워크로드 실습, 관측 기록 재생, 전용 로컬 kind

## 어떤 증거를 볼까
EKS 실습에서는 EC2 워커에서 demo/api Service로 직접 보낸 HTTP의 시각·응답·지연을 확인한다. Kubernetes API 조회·쓰기, Pod 생성·노드 할당, Ready, EndpointSlice는 각각 별도 증거다. Mac 터널이나 로그 회수가 실패하면 그 경로의 실패를 기록한다. 앱을 측정하지 못한 구간의 서비스 영향은 미확정이다.

## 위험 등급과 종료 판단
대표 서비스의 측정 구간 실패율이 5%를 초과하거나 p95 지연이 300ms를 초과하면 장애다. 연결 가능한 엔드포인트가 사라진 경우도 장애로 평가한다. 연결 대상이 없고 연속 두 유효 구간의 모든 요청이 실패하면 중대 장애다. 재생에서는 Ready 엔드포인트 0개를 실측한 시각 직전 20초 안의 두 묶음을 확인한다. 앱이 기준을 충족해도 배포·조회·쓰기 문제가 있거나 요청 지표가 비면 주의다. 요청과 운영 관측이 모두 안정적이면 정상이다. 서비스 영향을 판단할 표본이 부족하면 보류한다.
사건 중 확인한 영향과 마지막 확인 시점의 권장 처리를 따로 기록한다. 앱이 계속 응답해도 운영이 막혀 있으면 사람의 조치가 필요하다.

## 처리 방식과 권한
회복이 확인됐거나 일시적 신호가 사라지고 앱과 운영 상태가 안정되면 자동 관찰한다. 데모 echo는 연결 오류·시간 초과·HTTP 408·502·503·504에서 같은 본문을 한 번 재시도하고 200과 반환 내용까지 확인한다.
EKS 실측에서는 허용된 demo Deployment의 롤백·재시작·축소에 대해 실행 대상, 효과, 원문 절차와 운영자 승인을 확인한다. 복제본 증가와 노드·외부 자원 증설은 비용 및 용량 검토를 위해 사람에게 인계한다. 전용 로컬 kind의 demo/api에만 제한 자동 증설·롤백 절차를 적용한다.
Service, DNS, PVC, 노드, 권한, 자원 제한, EKS 관리형 제어 영역의 변경은 담당자에게 인계한다. 관측 기록 재생에서는 합성 기록과 실측을 표시하고 관찰 또는 사람 인계의 근거만 제시한다.

## 승인 가능한 실측 절차
[approval.scale] 비용 검토 대상이 아닌 복제본 변경은 현재 부하와 가용 용량, 목표 수를 확인하고 운영자 승인 후 허용 범위 안에서 실행한다.
[approval.restart] 외부 원인이 회복됐고 재시작으로 초기화할 대상과 영향이 확인되면 운영자 승인 후 해당 Deployment를 재시작한다.
[approval.rollback] 직전 정상 리비전과 현재 서비스 영향을 확인하고 운영자 승인 후 해당 Deployment를 롤백한다.

## 검증과 인계
명시적인 변경 요청에도 같은 실행 정책을 적용한다. 실행 직전에 대상 UID·세대·리비전을 다시 확인한다. 변경 후 목표 수, Ready, 엔드포인트와 같은 부하의 HTTP를 재측정한다. 앱 재시도, 자연 회복, 실험 도구의 정리, 운영자 작업은 실제 수행 주체로 기록한다. 인계할 때는 마지막 성공 단계, 실패 시각·대상·관측 지점, 원인 근거와 다음 확인 항목을 남긴다.
