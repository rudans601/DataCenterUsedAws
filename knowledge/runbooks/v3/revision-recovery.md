# 실패한 새 리비전의 격리와 롤백
버전 3.0 · 적용 대상 demo/api의 무상태 podinfo

## 원인 대조
배포 이력에서 바뀐 값과 새 리비전의 Pod·이벤트·로그를 대조한다. 직전 ReplicaSet이 아직 요청을 처리하는지, 새 리비전이 어느 노드에서 실패하는지를 확인한다. 현재 API의 서비스 장애 유무와 새 배포의 실패는 따로 판단한다.

## EKS 워크로드 복구
EKS 실습에서는 직전 정상 리비전, 변경된 필드, 기존 가용 복제본과 워커 HTTP를 확인한다. 대상 UID·세대·리비전이 관측 이후 바뀌면 다시 확인한다. EKS의 롤백은 운영자 승인 경로로 제안한다. 관측 기록 재생에는 실행 절차를 적용하지 않는다.

Recreate 배포에서는 기존 Pod가 먼저 종료되므로 `previous_available=0`만으로 이전 버전의 정상 여부나 복원 가능성을 부정하지 않는다. 장애 전 정상 HTTP·Ready·엔드포인트와 함께 기록한 Deployment UID·리비전·템플릿 해시를 현재 같은 Deployment 소유의 직전 ReplicaSet과 대조한다. 관측 전후 같은 배포이고 직전 템플릿이 당시 정상 버전과 일치한다면, 현재 이전 Pod가 0개여도 정상 복원 후보의 근거로 사용할 수 있다. 시각·소유자·템플릿이 맞지 않거나 정상 이력이 없으면 추측하지 말고 인계한다. 이는 승인 롤백의 근거이며 로컬 자동 롤백의 기존 가용 Pod 조건을 완화하지 않는다.

## 전용 kind의 제한 자동 조치
새 리비전의 Pod가 하나 이상 생성됐고 Ready가 0이며, 직전 리비전의 가용 복제본이 목표 수 이상이고 실제 요청과 엔드포인트가 정상인 경우에 적용한다. 실행 인자 또는 readiness HTTP 경로만 바뀌었고 그 변경과 현재 실패의 관계를 설명할 수 있어야 한다. Ready가 0이라는 사실만으로 롤백하지 않는다.

[auto.rollback] 전용 로컬 kind에서 이 조건을 모두 확인하면 demo/api를 가용 상태인 직전 리비전으로 롤백한다.

동일 Deployment가 최근 10분 안에 자동 변경됐다면 반복하지 않는다. 이미지·스토리지·자원 설정이 바뀌었거나 기존 버전이 서비스를 지탱하지 못하면 자동 롤백 범위를 벗어난다.
[approval.rollback] 복원할 버전과 영향이 확인되면 운영자 승인을 받고, 확인할 수 없으면 인계한다.

## 검증
기대한 템플릿으로 되돌아왔는지, 업데이트·가용·Ready 수가 목표와 같은지, 오류율 1% 이하와 p95 250ms 이하인지 확인한다. 배포가 막혔어도 기존 Pod가 요청을 받았다면 배포 복구와 서비스 중단을 구별해 보고한다.
