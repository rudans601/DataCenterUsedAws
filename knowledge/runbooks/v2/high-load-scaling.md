# 요청 급증과 CPU 포화
버전 2.0 · 적용 대상 demo/api

## 관측
평소와 현재 요청량, p95, CPU limit 대비 사용률과 스로틀링, Ready 수와 엔드포인트를 함께 비교한다. 일시적인 급증이 가라앉으면 다음 구간을 관찰한다. 요청량 변화 없이 새 리비전에서만 지연되면 배포 이력을 확인한다. DB 대기나 외부 연결 지연은 Pod를 늘려도 계속될 수 있다.

## 제한 자동 조치
지속적인 부하가 원인이고 현재와 직전 2분 구간 모두 p95가 300ms를 초과해야 한다. 현재 CPU 사용률 85% 이상 또는 스로틀링 25% 이상, 요청 계측 정상, Ready와 가용 복제본 충족, 연결 가능한 엔드포인트와 CPU·메모리 여유가 있는 워커를 확인한다.

[auto.scale] 조건을 모두 충족하면 demo/api 복제본을 정확히 1개 늘린다.

목표는 최대 6개다. 이미 증설 중이거나 최근 10분 내 자동 변경 이력이 있으면 자동 실행을 멈춘다.
[approval.scale] 더 큰 변경과 축소는 운영자 승인을 받는다.
노드 증설, 자원 요청 변경은 운영자가 검토한다.

## 검증
원래 부하가 계속되는 동안 새 Pod가 Ready인지 확인한다. 오류율 1% 이하, p95 250ms 이하와 함께 p95 20%, CPU 25%, 스로틀링 30% 중 한 가지 이상이 이전보다 낮아져야 증설 효과를 확인할 수 있다. 시험 부하가 먼저 끝나면 에이전트의 복구 성공으로 집계할 수 없다.
