# 운영 판단과 변경 권한
버전 2.0 · 적용 환경 KubeOps 로컬 실습

## 장애와 담당자 판단
정상 주소로 들어오는 요청과 엔드포인트를 먼저 확인한다. 실습에서는 한 측정 구간의 실패율이 5%를 넘거나 p95가 300ms를 넘으면 서비스 장애다. 전체 요청 성공률과 지연이 안정적이어도 새 Pod가 실패하거나 한 클라이언트가 잘못된 주소를 쓰면 주의로 기록한다. 연결 가능한 Pod가 없고 연속된 두 구간에서 모든 요청이 실패하면 중대 장애로 본다. 필요한 표본이 없으면 판단을 보류하고 확인할 자료를 적는다.

## 누가 처리할까
관찰은 서비스를 바꾸지 않고 요청을 다시 확인하는 조치다. 에이전트는 근거가 뒷받침하는 런북의 절차를 인용하고, 관찰·제한 자동 조치·승인 요청·사람 인계 가운데 한 가지를 고른다. 경고 한 줄, 최근 배포 시각, 과거 사례만으로 변경을 시작하지 않는다. 의심되는 운영 데이터와 런북의 적용 조건이 다르면 관측값과 부족한 근거를 사람에게 전달한다.

## 앱의 첫 대응과 인계
데모 echo는 같은 본문을 반복해도 상태를 변경하지 않는다. 연결 오류, 시간 초과, HTTP 408·502·503·504에는 같은 요청을 한 번 재시도하고 HTTP 200과 원래 응답 내용이 일치하는지 확인한다. 반복 실패, 잘못된 응답, 남아 있는 배포 이상은 현재 지표·이벤트와 함께 진단한다. 앱에서 회복한 요청은 앱의 처리 이력에 남긴다.

## 비용과 운영자 티켓
유료 노드·GPU·외부 자원 추가 또는 비용 여부가 불명확한 증설은 사람에게 인계한다. 비용 검토 대상으로 지정한 환경에서는 복제본 증가도 직접 실행하지 않는다. 티켓에는 대상, 판단 근거, 인용한 절차와 확인할 내용을 남긴다. 운영자는 티켓을 접수하고 수행한 작업과 확인 결과를 기록한다. 승인·거절과 실제 복구 성공은 별도로 기록한다.

## 변경 권한
로컬 실습의 demo/api에서만 제한 자동 조치를 검토한다. 자동 증설과 자동 롤백은 각 전용 절차의 모든 조건이 확인되어야 한다. 정상 버전이 확인된 일반 롤백, 일시적 초기화 실패의 재시작, 더 큰 증설이나 축소는 대상과 영향 확인 후 운영자 승인을 받는다. 대상은 demo의 Deployment이며 복제본 범위는 1~6개다. Service, DNS, 스토리지, 노드, 권한, 리소스 한도 변경은 담당 운영자에게 인계한다.

## 명시적인 운영 변경 요청
[approval.scale] 운영자가 대상과 목표 복제본 수를 명시하면 현재 부하와 여유 용량을 설명하고 승인 후 허용 범위 안에서 복제본 수를 조정한다.
[approval.restart] 대상의 일시적 장애와 재시작 효과를 확인하고 운영자 승인 후 해당 Deployment를 재시작한다.
[approval.rollback] 직전 정상 리비전과 현재 서비스 영향을 확인하고 운영자 승인 후 해당 Deployment를 롤백한다.

## 종료 기준
실행 직전에 대상과 리비전을 재확인한다. 변경이 실패하거나 서비스 회복 증거가 부족하면 추가 변경을 이어가지 않고 남은 증상과 마지막 측정값을 인계한다. 실험 주입 해제, 부하 종료, 운영자 직접 복원은 각각 기록한다. 사람이 검토한 문서만 운영 절차로 채택한다.
